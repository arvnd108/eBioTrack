## 2. Conventions

**Database**
- Tables and columns: `snake_case`. Table names plural (`samples`). Primary key `<singular>_id`.
- Foreign key columns keep the referenced key's name where possible (`site_id`, `event_id`). User references that mean something specific get a role name (`collector_id`, `operator_id`, `requested_by`).
- Every table has `created_at timestamptz NOT NULL DEFAULT now()` unless it is a pure link table or already has its own timestamp (`collected_at`, `changed_at`, ...).
- Enumerations are PostgreSQL `ENUM` types created in `001_extensions_and_enums.sql` (section 3). Lookup lists that users may extend (`sample_types`, `roles`, `dna_markers`, `laboratories`) are tables.
- Constraint names: `pk_<table>`, `fk_<table>_<column>`, `uq_<table>_<columns>`, `ck_<table>_<rule>`. Index names: `idx_<table>_<columns>`.
- SQL object names: views `v_<name>`, functions `fn_<name>` for helpers and plain verbs for procedures (section 7), triggers `trg_<table>_<purpose>`.

**Files** (follows [ARCHITECTURE](ARCHITECTURE.md))
- A slice's SQL lives only in that slice's files. Cross-slice foreign keys live only in `090_cross_slice_constraints.sql`.

**Code**
- Controllers contain no SQL. Services call parameterized queries, views, and the stored procedures in section 7.
- Business rules that must always hold live in the database; the API maps database errors to HTTP errors (section 7).

## 7. Stored procedure and function signatures

All are PostgreSQL functions called from the backend with parameterized queries (`SELECT register_sample($1, $2, ...)`). Each runs as one transaction. Names and argument order are part of the contract; bodies belong to the slice owner.

### Acting user and audit

The backend sets the acting user for every request that writes, inside the transaction:

```sql
SET LOCAL app.current_user_id = '<user_id>';
```

The audit trigger function reads it with `current_setting('app.current_user_id', true)` and stores it in `audit_logs.actor_id`.

**C: audit trigger function**

```sql
CREATE FUNCTION audit_row_change() RETURNS trigger
```

Attached as `AFTER INSERT OR UPDATE OR DELETE` row triggers. The primary key column name is passed as `TG_ARGV[0]` (for example `CREATE TRIGGER trg_samples_audit ... EXECUTE FUNCTION audit_row_change('sample_id')`). A, B, and D attach it to their tables after C merges it.

### Procedures

| Owner | Signature | Returns | What it does |
|---|---|---|---|
| C | `create_project_with_owner(p_title text, p_objectives text, p_start_date date, p_owner_id bigint)` | `project_id` bigint | Creates the project and the owner membership in one transaction |
| D | `register_sample(p_event_id bigint, p_sample_type_id bigint, p_volume_ml numeric, p_depth_m numeric, p_storage_location text, p_actor_id bigint)` | `sample_id` bigint | Generates the sample code, inserts the sample as `collected`, writes the first history row |

| A | `import_detections(p_analysis_id bigint, p_rows jsonb, p_actor_id bigint)` | inserted row count integer | Inserts all rows in one transaction; any invalid row raises an error and **nothing** is inserted; moves the analysis to `imported`. Row shape in section 12 |

| A | `reject_analysis(p_analysis_id bigint, p_actor_id bigint, p_reason text)` | void | Moves a `draft` or `imported` analysis to `rejected` and records the reason in the audit entry |

Status changes for samples, extractions, and runs that do not need a procedure are plain `UPDATE`s; the triggers enforce the allowed transitions.

### Errors

Procedures and triggers raise exceptions with these SQLSTATE codes. The API maps them to HTTP errors.

| SQLSTATE | Meaning | HTTP status | API error code |
|---|---|---|---|
| `EB001` | Invalid state transition | 409 | `invalid_transition` |
| `EB002` | Business rule violated (failed QC, bad row, booking rule, wrong approver) | 422 | `rule_violation` |
| `EB003` | Already processed or concurrent conflict (for example second approval) | 409 | `conflict` |
| `23505` | Unique violation | 409 | `duplicate` |
| `23503` | Foreign key violation | 422 | `invalid_reference` |
| `23514` | CHECK violation | 422 | `validation_error` |

The exception message is a short human-readable sentence; extra detail goes in `DETAIL`.

## 8. API conventions

- **Base path:** `/api`. JSON in, JSON out, UTF-8. CSV only for imports and exports.
- **Field names:** `snake_case` (D15). Timestamps ISO 8601 UTC (`2026-03-12T09:30:00Z`); dates `YYYY-MM-DD`.
- **IDs:** numbers.
- **Auth:** session cookie `ebiotrack.sid`. Not signed in → `401`. Signed in but not allowed → `403`. Project data a user is not a member of returns `404`.
- **Success envelope:** `{ "data": <object or array> }`. Lists add `"meta": { "page": 1, "limit": 25, "total": 130 }`.
- **Pagination:** `?page=1&limit=25` (default 25, max 100). List endpoints also accept `?sort=<field>` or `?sort=-<field>` where useful.
- **Error envelope:**

```json
{ "error": { "code": "validation_error", "message": "Latitude must be between -90 and 90", "details": [ { "field": "latitude", "message": "out of range" } ] } }
```

- **Status codes:** `200` OK, `201` created, `204` no content, `400` malformed, `401`, `403`, `404`, `409` conflict, `422` validation or rule failure.
- **Writes** run in a transaction that first sets `app.current_user_id` (section 7).
- **Filters** are query parameters named after the column (`site_id`, `status`, `from`, `to`).

## 12. Detection CSV import format

Used by `POST /api/analyses/import` and `import_detections()`.

- UTF-8, comma-separated, header row required, maximum 10 MB.
- Columns, exactly these names in any order:

| Column | Rules |
|---|---|
| `library_code` | Required. Must exist and belong to the sequencing run of the target analysis |
| `scientific_name` | Required. Must match an existing taxon with the given rank (D16) |
| `taxon_rank` | Required. One of the `taxon_rank` values |
| `read_count` | Required. Integer ≥ 0 |
| `confidence` | Required. Number from 0 to 1 |
| `qc_flag` | Required. `pass`, `warn`, or `fail` |

- A row repeating the same `library_code` + taxon is rejected.
- The whole file imports or none of it does. Errors are reported by row number (header = row 1) with the field name.

`import_detections()` receives the validated rows as JSON:

```json
[ { "library_code": "LIB-0001", "taxon_id": 8, "read_count": 1450, "confidence": 0.9731, "qc_flag": "pass" } ]
```

The backend resolves `scientific_name` and `taxon_rank` to `taxon_id` before calling it; the procedure still re-checks every row.

`datasets/sample_detections.csv` and `tests/fixtures/detections_valid.csv` must follow this format; `detections_invalid_row.csv` must contain exactly one bad row.
